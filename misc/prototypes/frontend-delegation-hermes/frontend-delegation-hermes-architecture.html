Voice Frontend Delegation to a Hermes Backend: architecture

Prototype in src/prototypes/voice_delegation_hermes_agent/. An OpenAI Realtime (GA) voice agent made of two agents decoupled in time: a fast frontend LLM that only routes and speaks fillers, and a slow reasoning Hermes backend that does the work, one worker process per session.

How it works

A fast frontend LLM keeps the conversation going; a reasoning backend does the work in the background. Fast path: the user hears a filler immediately. Slow path: the answer is spoken when the backend finishes.

The delegate tool and the Hermes calls

The frontend LLM calls delegate() once per user turn; the gateway turns it into a Hermes call.

Appendix C. One delegated turn, end to end

  1. Client streams mic audio over WS /v1/realtime; VAD ends the turn after 800 ms of silence; Riva ASR returns the transcript, which is normalized (spelled letters joined).
  2. Frontend lane: the spelling hold may wait; the LLMDecider forces one delegate call (hedged at 1.5 s, repaired once, 4 s timeout). New speech before it returns cancels it and merges into the next transcript.
  3. The filler goes to the OutputQueue and is spoken at once through TTS; the same turn is sent as delegate (turn_id, request, run_input) over BackendLink.
  4. Gateway: the controller settles the previous run, renders the context-queue entries into the next user message, and sends run / steer / redirect / status to the worker (state-dependent, section 2).
  5. Worker: Hermes AIAgent reasons with nemotron-3-ultra and calls session tools. Each tool call becomes tool.call and blocks in ToolFutures.
  6. Tool round trip: gateway → voice server → ToolRelay (screen arguments, batch 30 ms) → client function_call; the client's output returns through ResultHints (recovery note on a failed lookup) → tool.result → worker unblocks.
  7. While WORKING, activity events are kept as recent backend activity for the frontend's next decision, and M1 can speak one proactive line after 15 s of silence. A request=status turn is answered from the status summary, put into words by the status verbalizer.
  8. The worker emits run_outcome; the controller commits history, sends answer and backend_run_done; the output lane cleans the text (G2) and speaks it, recording heard / partial / not_heard in the transcript.
