# τ³ Voice FDH: fix plan for the top geval failure classes (with no-regression gates)

A concrete plan for the three failure classes that dominate the `geval` runs of the Frontend Delegation Agent (FDH):

1. wrong or unconfirmed changes;
2. transfers handled wrong;
3. identification that still fails.

Every proposed change must be **purely beneficial**: it may not change the behaviour of a task that passes today.
**No change in this plan is guaranteed safe**, including the code fix A1. Every change can only be **shown, within
measurement limits,** not to regress (§5), and all changes are blocked until their gates pass. A1 has the narrowest
trigger, not a safety guarantee.

The valid geval runs are airline 0.660, retail r3 0.711 and telecom 0.684, with **86 failed tasks**

infrastructure failures ([R13](../../../../voice-agent-evaluation-dump/tau-3-voice/2026-10-05_05-59-44Z_fdh-voice-geval/observations/2026-10-07_retail-r2-vs-r3-variance.md),
[R9](../../../../voice-agent-evaluation-dump/tau-3-voice/2026-10-05_05-59-44Z_fdh-voice-geval/fdh_voice_geval_retail_regular/observations/2026-10-07_fdh-voice-retail-r1-geval-analysis.md)). Three classes account for 51 of the 86:

| # | Issue | Failures | Root causes found | Fixes |
|---|---|---|---|---|
| 1 | The agent changes things without a clear yes, or against the rules | 20 | no consent to the exact change (7); a change the policy forbids (4); incomplete search or scope (7); a required fix skipped (2, telecom) | B1, B2, B3, C1 |
| 2 | The agent hands calls to a human too early | 14 | transferred with required steps still open (11, telecom); a false "can't do that", then transfer (3) | C1, C2 |
| 3 | Identifying the caller still fails | 17 | phone in the wrong format, never retried (4); misheard name never re-spelled or the spelling unused (5); ASR lost the characters (6); no lookup attempted (2) | A1, A2, A3; ASR is out of scope |

**What the plan proposes:**
- **One code fix with the narrowest trigger** (A1): when a lookup tool's **phone field** returns not-found, the
  tool relay retries the same digits in the other common format.
  - It runs only on tools that **declare** read-only semantics; names and descriptions never suffice.
  - Where no tool declares this (τ³'s schemas today), the path is **A1-lite**, a hint, which gets the full
    prompt-change gates.
  - Its risks are stated, not assumed away: a misheard number in the other format can match a different account.
- **One prompt de-conflict** (A2): the backend prompt currently gives the model three instructions, two of which
  forbid the format retry.
- **Five narrowly-scoped prompt rules** (A3, B1, B2, B3, C1, C2), each behind its own flag.
  - Prompt rules change model behaviour everywhere, so they **cannot be proven harmless offline**.
  - Each is accepted only if all of the following hold (§5):
    - the decision replay (G2) reproduces every **unchanged** write and transfer of today's passing tasks, and turns
      every **expected policy correction** into a confirmation followed by the same write;
    - a paired A/B against a **clean, 429-free** control (G4) shows no regression beyond the measured run-to-run
      noise, for each fix alone and for all fixes combined;
    - every task that passed in control and fails in the arm has been investigated and explained.
  - Even then, the result is evidence within measurement limits, not a guarantee.
- **Prerequisites** (P0): a 429 gate, so A/B runs are valid, and a backend decision trace, so the replay gate can
  exist. Both are logging and gating only.
- **Kept separate** (track I, §4): retry timing, fallback models and spoken updates change what the caller
  experiences, so they can move scores. They are not prerequisites and are validated on their own.

**Rejected because they are trade-offs:** three tempting designs were measured against today's passing tasks and
rejected, because each would have changed passing behaviour (§3.2):
- a hard "no write without a yes" gate;
- a hard "no transfer unless the user asked" gate;
- a "spell the field that keeps failing" directive.

**Targets:** the fixes target **43 of the 86 failures**:
- A1: 4;
- A3: 5;
- B1: 7;
- B2: 4;
- B3: 7;
- C1: 13;
- C2: 3.

Targeted is not the same as fixed. These are targets, not a forecast (§7).

## 3. The no-regression rule

### 3.1 Fix tiers

| Tier | What it is | Why it can't hurt a passing task | Gates (§5) |
|---|---|---|---|
| **Code, failure-triggered** (A1) | Deterministic code that runs only after a lookup has already failed, on declared read-only tools | Narrowest trigger, not a guarantee: a triggered task's conversation changes, and a format match can be a wrong account | G0 unit tests, G1 log replay across domains, G3 mock and invented scenarios, G4 paired A/B |
| **Prompt, flagged** (A1-lite, A2, A3, B1–B3, C1, C2) | One `prompt_features` flag per rule, a narrow wording ("only when …"), invented examples | Not provable offline: a prompt changes the model's distribution | G2 decision replay (unchanged decisions reproduced; expected policy corrections checked through confirmation and completion), G3 mock and invented scenarios, G4 paired A/B against a clean control (5 trials; each fix and combined) |
| **Infra, evaluation (P0)** | Evaluation hygiene: run gates, logging | No agent behaviour change: logging and gating only | Run checks |
| **Infra, runtime (track I)** | Retry timing, fallback endpoints, spoken progress | **Changes the call**, so it can move scores either way | Its own G2–G4 cycle, never combined with an A–C arm |

A change that fails its gates is **not shipped**. The fix is rewritten using non-scored data only (mock, invented
cases), never by iterating against the scored logs (§8).

### 3.2 Designs rejected after measuring them on passing tasks

| Design | Measured on the valid geval runs | Verdict |
|---|---|---|
| **Hard consent gate:** a write tool is answered locally ("not done, ask for a yes") unless the user's last utterance is affirmative | [E1](../../../../voice-agent-evaluation-dump/tau-3-voice/2026-10-05_05-59-44Z_fdh-voice-geval/observations/data/fixplan_writes_consent.txt): 50 writes in **passing** tasks would have been intercepted (airline 8, retail 15, telecom 27). The user's last words were "Any update?", "Hello? You still there?", a payment detail ("Gift card…"), or an offer ("I can refuel two point zero GB"), with consent given earlier or implied by the request | **Rejected.** A keyword gate can't tell an earlier, valid confirmation from none, so it would add turns or derail passing tasks. B1 (prompt) enforces the policy's own confirmation rule instead |
| **Hard transfer gate:** answer `transfer_to_human_agents` locally unless the user asked for a human | [E2](../../../../voice-agent-evaluation-dump/tau-3-voice/2026-10-05_05-59-44Z_fdh-voice-geval/observations/data/fixplan_transfers.txt): 36 transfers in **passing** tasks were made without the user asking (airline 8, retail 10, telecom 18). They are policy-required transfers (PIN-locked SIM, ended contract, out-of-scope requests) | **Rejected.** C1 (prompt) keys on the policy, not on whether the user asked |
| **"Spell the field that keeps failing" directive:** on repeated name misses, name the repeated field and ask for its spelling | [E3](../../../../voice-agent-evaluation-dump/tau-3-voice/2026-10-05_05-59-44Z_fdh-voice-geval/observations/data/fixplan_name_misses.txt): in the 17 r3 tasks with the same name value in ≥2 failed lookups, the repeated value was **correct** in about half; in passing tasks 17, 49 and 91 another field was wrong. A directive would misdirect them | **Rejected.** A3 only *informs* (which values were spelled and which only heard) and does not direct |

## 4. The fixes

Each fix lists its targets (task ids in the valid geval runs), the change, its trigger, why it is safe, its flag and
its tests. Prompt texts use **invented examples only** (§8).

### A1 (code): same-digits format retry in the tool relay

**Targets:** telecom #24, #70, #86, #92 (`id_format`). It also identifies earlier in #13, #29 and #93, which failed
later for other reasons, and in 8 passing tasks.

**Change:** in [`tools/relay.py`](../../../src/prototypes/voice_delegation_hermes_agent/tools/relay.py), when `on_function_output` receives a permanent
failure (the `retry_guard` pattern in [`config/voice/realtime_eval.yaml`](../../../src/prototypes/voice_delegation_hermes_agent/config/voice/realtime_eval.yaml)),
retry only if **all** of these hold:

1. **A declared read-only tool.** The tool's schema declares read-only, idempotent semantics, for example
   `annotations: {readOnlyHint: true, idempotentHint: true}` (the MCP tool-annotation convention), or the client
   declares the same in its session setup.
   - The name prefix, the description and the schema read/write split
     ([`is_read_tool`](../../../src/prototypes/voice_frontend_backend_agent/normalization/schema_rules.py)) are **not** sufficient: they don't prove the
     call has no side effects.
   - Without a declaration, A1 does not issue a call, and A1-lite applies instead.
   - τ³'s tool schemas carry no such annotation today, so **on τ³ the deployed path is A1-lite** unless the client
     protocol adds declarations.
2. **A genuine phone field.** The argument's *name* contains `phone`, `mobile`, `msisdn` or `telephone`, or its
   schema *description* says "phone number". A value that merely has 10 digits never qualifies.
   - Retail `product_id` and `item_id` values are 10-digit numbers (for example `9523456873`), so a shape-only rule
     would have retried them as `952-345-6873`.
3. **A 10-digit value.** Digits only becomes `XXX-XXX-XXXX`; a value with `-`, `.`, space or parentheses becomes
   digits only. Any other digit count gets no retry.
4. **No schema rule and no known failure.** The argument has no schema rule (`schema_rules.py` would already
   canonicalise it), the other form is not already a known failure key, and A1 hasn't retried this value before.

If they all hold, emit **one** extra function call with the other form (a synthetic call id `"<id>.fmt"`) in its own
batch. The original call's result is withheld until the retry settles:

| Retry outcome | Result returned for the original call | Failure keys |
|---|---|---|
| Found | The retry's output, prefixed `[Looked up as 555-867-5309: same digits, other format.]` | Only the **original** form is marked failed. The successful form is never marked failed, so the backend can repeat it later |
| Not found (permanent failure) | The original failure plus `[Also not found as 555-867-5309.]`, then the normal I3/I4 hint | Both forms marked failed |
| Transient error, timeout or no output within `tools.result_timeout_s` | The **original** failure, unchanged, with the normal hint; the retry is dropped | Only the original form; the other form stays unmarked, so the backend may still try it |
| Original call cancelled (`on_cancel`: interrupt, new epoch, worker died) | Nothing is sent (as today). The synthetic call is cancelled too, and its late output is ignored like any cancelled id | Only the original form |
| Retry output arrives for a stale epoch | Ignored | No change |

Log `format_retry {tool, argument, before, after, outcome: found | not_found | timeout | cancelled}`.
`take_ack` treats the synthetic batch like any other batch, and tests must show it never consumes the original
batch's acknowledgement.

*Implementation note:* the synthetic call is emitted only after the original batch's acknowledgement, so it never
shares or consumes that acknowledgement. The `format_retry` event also logs `mode`, and its outcomes add `hint`
(A1-lite) and `transient`. The flag is `format_retry: {enabled, mode: call | hint, fields: phone}`.

**A1-lite**, for tools without a read-only declaration (τ³ today), or if the synthetic call complicates the wire
protocol (batch acknowledgement in `take_ack`):
- append to the not-found output of a genuine phone field (rules 2–4 above): `[Same digits in the other common
  format: 555-867-5309. Look that up once before asking the user.]`;
- it issues no call itself; the backend decides. It costs one model turn and needs model compliance.
- **It is a prompt-visible change, so it gets the full prompt-change gates:** G0, G1 (that the hint text appears
  exactly where specified), G2, G3 and G4. Its flag is separate from A1's (`format_retry: {mode: hint}`).

**Trigger:** only a not-found result on a genuine phone field of a safe lookup tool, once per value.

**Why the risk is small, and what remains:**
- Passing paths with no failed phone lookup are byte-identical (G1).
- A scan of **every** failed read call in the valid runs found no 10-digit value in any non-phone argument. Still,
  rule 2 (field, not shape) is required for retail-like schemas.
- 20 of 278 valid-run tasks hit the trigger ([E4](../../../../voice-agent-evaluation-dump/tau-3-voice/2026-10-05_05-59-44Z_fdh-voice-geval/observations/data/fixplan_phone_lookups.txt)), all on telecom: 11 passing and 9 failing. Telecom #25's `5-123-2002`
  is not phone-shaped, so it doesn't trigger.
  - In 8 passing tasks (#14, 23, 53, 69, 75, 82, 83, 99) the failed value was the undashed form of the right number,
    so A1 identifies the caller immediately. In #53 this happened only after 243 s; #83 passed without ever
    identifying the caller.
  - In 3 passing tasks (#54, 67, 95) the digits were misheard, so A1 adds one read call (about 0.3 s, no model turn)
    that also fails, and the existing flow continues unchanged.
- **Wrong-account risk (not excluded).** If the user's number was misheard, the misheard digits in the other
  format can belong to a **different** real account, and A1 would return it as found.
  - The same risk exists today when the backend retries the format itself, as the `<phone_numbers>` prompt asks;
    A1 makes it automatic.
  - Mitigations:
    - A1 returns the found result with the note `[Found only after a format change; verify the caller as your
      policy requires before acting on this account.]`;
    - A1 never writes;
    - G1 compares, in every replayed found-after-retry case, the identity found with the task's expected identity,
      and any mismatch rejects A1;
    - G4 includes it.
- **Side-effect risk.** This is handled by rule 1: A1 only calls tools whose read-only semantics are declared, never
  inferred.

**Flag:** `normalization.tool_arguments.format_retry: {enabled: false, fields: phone}`, off by default.

**Tests:**
- Invented tools that **should** retry: `find_account(phone)`, `lookup_member(mobile_number)`.
- Invented tools that **must not** retry:
  - `get_item(item_id="1234567890")`, `get_order(order_number="5551234567")` (a 10-digit non-phone);
  - `update_contact(phone)` (a write);
  - `get_status(phone)` **without** a read-only declaration (falls back to A1-lite);
  - `send_code(phone)` declared read-only by mistake: covered by a review checklist for declarations, not by code.
- A found-after-retry result carries the verify note.
- **Across domains (G1, G3):**
  - replay the clean controls of airline, retail, telecom and mock;
  - A1 or A1-lite must trigger only on phone fields;
  - outputs elsewhere byte-identical;
  - every found-after-retry identity equal to the expected one.
- Both directions, and a value with 9 or 11 digits.
- One retry per value.
- Each row of the outcome table, including a cancellation while the retry is in flight and a retry timeout.
- Batch acknowledgement intact.
- A found retry leaves its form unmarked.

### A2 (prompt): remove the format-retry contradiction

**Targets:** the A1 cases when A1 is off or a format other than a phone number is involved; consistency.

**Change**, two wording edits and no new behaviour:
- In [`prompts.backend.yaml`](../../../src/prototypes/voice_delegation_hermes_agent/config/prompts.backend.yaml) `spelling_v2`, after "do not retry with a guess or a variant", add: *"(changing only
  separators or letter case, with exactly the same characters, is a format correction and not a variant)"*.
- In `lookup_not_found_hint` ([`prompts.voice.yaml:410`](../../../src/prototypes/voice_frontend_backend_agent/config/prompts.voice.yaml)), add one sentence before "Ask about one field": *"If a value
  may only be in the wrong format (the same characters with different separators or case), look it up once in the
  other format before asking the user."*

**Trigger:** it is the same prompt in every session, but it only changes what the model may do after a failed lookup.

**Why it is safe:**
- It removes a contradiction rather than adding a behaviour.
- Its scope ("exactly the same characters") excludes guesses, so the reason `spelling_v2` exists (no invented
  variants) is preserved.
- Still a prompt change, so gates G2–G4 apply.

**Flag:** `prompt_features.format_correction` (backend) plus a hint-catalog variant key.

### A3 (prompt, information only): spelled versus heard fields on repeated misses

**Targets:**
- retail r3 94 and 99: "Lei"→"Leigh" and "Sofia Li"→"Sophia Lee", never re-spelled;
- retail r3 52: the spelled "S-O-F-I-A" was available, but the lookup used the heard "Sophia";
- retail r3 78 and 81: a spelled email was not used for the next lookup.

**Change:**
- `ResultHints` ([`tools/result_hints.py`](../../../src/prototypes/voice_delegation_hermes_agent/tools/result_hints.py), built in
  [`server.py:122`](../../../src/prototypes/voice_delegation_hermes_agent/server.py)) gets a per-session provider of the values the user **spelled**, from the
  voice server's transcript normaliser ([`engine/transcript.py`](../../../src/prototypes/voice_delegation_hermes_agent/engine/transcript.py)): the written forms
  of `spelled_runs` spans.
- On the **second and later** person-lookup miss, the appended note gets one factual line, for example:
  `Fields in this lookup: first_name "Leigh" (heard as a word), last_name "Wilson" (unknown), zip "32255" (unknown).`
- If a spelled value associated with a field (see below) differs from the value sent, the line also says:
  `(the user spelled "SOFIA" for the first name)`.
- **Attribution needs a field association and a turn association; otherwise it is `unknown`.** A value matching some
  text is not enough, because a match doesn't show which field or which person the value belongs to.
  - **Turn association.** The evidence must come from one user turn that answers a request for that specific field,
    either:
    - the agent's immediately preceding question asked for exactly that one field ("Could you spell your first
      name?"); or
    - the user names the field in the same turn ("my last name is L, I").
    - A turn that answers several fields, or names several people (for example passengers, or another account
      holder), is `unknown` for all of them, unless each value sits next to its own field name and person.
  - **Exact match.** The span's written form must equal the sent value **character for character**, ignoring only
    letter case. Any difference in separators, spaces, punctuation or digits means `unknown`.
  - `spelled` requires a `spelled_runs` span meeting both conditions.
  - `heard as a word` requires the value to appear as a plain word in that associated turn, with no spelled span
    overlapping it.
  - **Digit-only values are never `spelled`.** `spelled_runs` only forms a run that contains at least one letter
    ([`normalization/transcript.py`](../../../src/prototypes/voice_frontend_backend_agent/normalization/transcript.py) l. 20–22 and `close()`), so a
    spoken ZIP or phone number never produces a spelled span. Such fields are reported `unknown`, unless a future
    digit-run detector provides the same field and turn association.
  - Everything else is `unknown`: merged spelling holds, partial matches, a value the backend reshaped, evidence from
    an earlier field request that was later corrected.
- No instruction about which field is wrong; the existing I4 text keeps the decision with the model.
- *Implementation note* ([`tools/field_provenance.py`](../../../src/prototypes/voice_delegation_hermes_agent/tools/field_provenance.py)):
  the "unless each value sits next to its own field name and person" exception is not implemented. A turn with two
  or more spelled spans is `unknown` for every field, which is the conservative choice.
- **Tests:**
  - each attribution class;
  - a matching span in a turn that answered another field's request → `unknown`;
  - a two-person turn → `unknown`;
  - separators differ → `unknown`;
  - a digit-only ZIP → `unknown`;
  - a spelled span split across two holds → `unknown` unless the merged hold reproduces the value exactly, in a
    turn associated with that field.

**Trigger:** only the ≥2nd miss of a person lookup in a session.

**Why it is safe:**
- It adds facts, not directives; the rejected directive variant (§3.2) would have misdirected about half the passing
  cases.
- Still a prompt-visible change, so G2–G4 apply.
- The exposure is 9 passing r3 tasks with repeated name misses, all inspected by the G2 replay.

**Flag:** `normalization.tool_arguments.result_hints.field_provenance: false`.

### B1 (prompt): consent to the exact change

**Targets:**
- airline 12: upgraded both passengers for $1,200 before quoting it;
- retail r3 18 and 71: wrote on a request, with no summary and no yes;
- retail r3 25: a tracking-number read-back taken as consent;
- retail r3 93: wrote on a half-heard turn;
- retail r3 21: the summary was cut off and "go ahead" was taken as consent;
- retail r3 98: "the other card" ignored.

**Change:** extend `<consent>` in [`prompts.backend.yaml`](../../../src/prototypes/voice_delegation_hermes_agent/config/prompts.backend.yaml) behind a new flag
`write_consent_v2` (registered in [`prompt_features.py`](../../../src/prototypes/voice_delegation_hermes_agent/prompt_features.py) `BACKEND_FEATURES` and
pinned in [`gateway.eval.yaml`](../../../src/prototypes/voice_delegation_hermes_agent/config/gateway.eval.yaml)):

```
Your policy decides when a change needs the user's confirmation, and how. When it requires you to
list the details and get an explicit yes, do exactly that before calling a tool that changes
anything: say what will change, any amount charged or refunded, and the payment method, then wait
for a clear yes to that summary. A request, even one that names the change, is not that yes. These
are never a yes: a question, the user reading a number back, an unfinished sentence, or "go ahead"
after your summary was cut off; in those cases repeat the summary. A yes you already received for
the same summary still counts after later small talk or "are you there?". If the user named a
payment method, use it; if they referred to one indirectly (for example "the other card"), ask
which one before you summarise.
```

**Trigger:** every write the backend considers. Where the policy requires confirmation, the rule adds the
confirmation; where it doesn't, the rule only forbids treating questions and fragments as agreement.

**Why it can still be safe:**
- It enforces the policy's own rule. Airline ([`policy.md` l. 7](../../../../tau2-bench-smasurekar/data/tau2/domains/airline/policy.md)) and retail
  ([`policy.md` l. 16](../../../../tau2-bench-smasurekar/data/tau2/domains/retail/policy.md)) both say "you must list the action details and obtain
  explicit user confirmation (yes) to proceed".
- A write made on a direct request without that yes was already non-compliant, even when tau2 scored the task as
  passed.
- "A yes you already received … still counts" keeps writes that happen after pings, the main pattern among the 50
  passing writes the rejected hard gate would have intercepted ([E1](../../../../voice-agent-evaluation-dump/tau-3-voice/2026-10-05_05-59-44Z_fdh-voice-geval/observations/data/fixplan_writes_consent.txt)).

**Higher exposure than r1:** passing tasks where the backend wrote on a direct request, with no summary-and-yes, will
now get one extra confirmation turn. That is policy-correct, but it changes the conversation, and the simulated user
may react to it.
- G2 labels every such write **P** (expected policy correction). It is checked through the confirmation and then
  the same write, not required to happen immediately (§5).
- G4 must show that those tasks still pass, end to end.
- Before G2, E1 is to be refined to separate "explicit yes to a summary earlier in the call" from "no confirmation at
  all", to size this exposure.

**Proof obligation:** G2 covers all 274 write/transfer calls of the 167 passing tasks with writes (airline 35,
retail r3 139, telecom 100; in the clean controls these numbers are re-counted). U-labelled calls must be
reproduced unchanged; P-labelled calls must become a confirmation followed by the same write (§5). Then G4.

### B2 (prompt): policy check before every write

**Targets:**
- airline 1: cancelled a non-refundable booking;
- airline 14: changed a basic-economy booking;
- airline 29: changed the destination;
- airline 30: removed a bag the policy keeps.

**Change:** new `<before_change>` block, flag `policy_check`:

```
Before you call a tool that changes anything, check what your policy says about that exact
change, for example limits by product or fare type, membership level, time since purchase, or
which fields may be changed. Many limits allow a change under conditions, or allow part of it, and
some have stated exceptions; check whether the conditions or an exception apply. Refuse only what
a rule actually forbids for this case. If the policy allows only part of what the user asked for,
or allows it only in a different form, explain which part is not allowed and why, describe the
change that is allowed, and make it only after the user agrees to that change (with an explicit
yes to its summary when your policy requires one). Never make a reduced or different change on
the strength of the original request alone.
```

**Why it can be safe:**
- It only adds a check the policy already requires.
- It is worded to **allow within limits**: conditional rules, partial changes and stated exceptions are named
  explicitly. Examples of the kinds of exception, not to be pasted into the prompt:
  - a cancellation allowed within a time window, or with insurance;
  - one field changeable while another isn't.
- **A partial or different change needs fresh agreement.** If what the policy allows differs from what the user
  asked, the user must agree to the allowed change before it is made. This is consistent with B1.
- A passing tau2 database check does **not** prove a write was policy-compliant: the DB check compares the final
  state, not the path or the confirmation. B2's over-refusal risk is therefore measured directly (below), not
  inferred from passing scores.

**Main risk: over-refusal.** The model may misread a limit as a ban.
- G2 must reproduce every passing write; any write refused in the replay rejects B2 as worded.
- G3 adds invented cases where a change is allowed only under a condition or exception, and where only part is
  allowed. Each must be carried out, not refused.

### B3 (prompt): cover the whole request

**Targets:**
- airline 24: searched one of the two requested airports;
- airline 21: the fastest option not ranked by duration;
- airline 42: did not check every reservation against the plan;
- retail r3 20: "all items" narrowed to one;
- retail r3 37: "cheapest" not taken across all variants;
- retail r3 79: did not look up the other order;
- retail r3 103: a requested change never made.

**Change:** add to `<before_change>`, flag `request_scope`:

```
If the request covers several records or uses words like "all", "both", "each" or "every", look up
each one and include all of them before you act. If it asks for the best option by some measure
(cheapest, fastest, earliest), compare every option your tools return for all the places or
dates the user allowed, then choose. Before you finish, check that every part of the request
was done or answered.
```

**Why it is safe (design):** it adds reads before acting; it doesn't change which writes are allowed. The cost is
extra lookups; G4 checks that call length doesn't push passing tasks into breakdowns or `max_steps`.

### C1 (prompt): remaining-steps check before transfer

**Targets:**
- telecom #3, 4, 17, 19, 20, 22, 26, 30, 35, 38, 46 (`transfer_wrong`);
- telecom #13 and #81 (a required fix skipped, then stopped).

**Change:** new `<before_transfer>` block, flag `transfer_check`:

```
Follow your policy on transfers exactly: when it requires a transfer for the situation, transfer
without delay; when it says to transfer only if the request cannot be handled with your tools,
transfer only then. Before a transfer that the policy does not require right away, check the
steps that your policy and any troubleshooting guide in your instructions give for the problem
the user reported. Do the remaining steps that apply to that problem and that you are allowed to
take, getting the user's agreement where the policy requires it, and skip steps that do not
apply or that the policy does not allow. Base this on what the user reported most recently. Call
the transfer tool before you tell the user you are transferring them.
```

**Why it can be safe:**
- **Required transfers come first and are never delayed.** This keeps the 36 passing policy-required transfers (the
  reason the hard gate was rejected). Example situations, not to be pasted into the prompt: a locked SIM, a suspended
  contract, a flight already flown.
- **The scope matches the policy.** "If and only if the request cannot be handled within the scope of your actions"
  appears in the airline, retail and telecom policies ([airline l. 15](../../../../tau2-bench-smasurekar/data/tau2/domains/airline/policy.md),
  [retail l. 24](../../../../tau2-bench-smasurekar/data/tau2/domains/retail/policy.md), [telecom l. 13](../../../../tau2-bench-smasurekar/data/tau2/domains/telecom/main_policy.md)). Telecom
  adds "try your best to resolve the issue … before transferring" (l. 15). The r1 wording "when the user still wants
  one" went beyond the policy and has been removed.
- **Only relevant, authorized steps.** Steps must apply to the problem the user reported and be within what the
  agent may do, with the user's agreement where the policy requires it. So C1 cannot push unrelated or unauthorized
  actions.
- "What the user reported most recently" addresses #4 and #38 (stale state).
- G2 must reproduce all 54 passing transfers (airline 18, retail r3 17, telecom 19), at the same point in the call.
  A transfer that the replay delays by extra steps counts as a regression.

### C2 (prompt): capability check before "I can't"

**Targets:**
- airline 44: "my tools can't show times", though `search_direct_flight` does;
- airline 32: called a fare change impossible, using one leg's price;
- retail r3 77: transferred a new-order request instead of saying it is not possible and offering an exchange.

**Change:** add to `<before_transfer>`, flag `capability_check`:

```
Before you tell the user that something is impossible or that your tools can't do or show it,
check your tool list and the tool descriptions; if a tool can, use it. If the request is still
outside what your tools and policy allow, follow the policy's required refusal, alternative, or
transfer for that case.
```

**Why it can be safe:**
- It adds a check before a negative answer.
- For a genuinely out-of-scope request, it defers to the policy: refuse, offer the allowed alternative, or transfer
  where the policy requires one. It never prefers an alternative over a required transfer, so it is consistent with
  C1.
- G2 covers it, since all passing transfers are in the unchanged-decision set (§5).
- r3 77 (a new-order request) is fixed only if the policy's answer for it is a refusal with an alternative. That is
  the policy's call, not this rule's.

## 5. Validation gates

The gates are applied per fix, in order. A fix that fails a gate is not shipped.

| Gate | What | Pass criterion | Fixes |
|---|---|---|---|
| **G0** Unit tests, invented data | Made-up tool schemas and values (no τ-bench names) | All pass. Off-switch renders byte-identical prompts (as [`prompt_features.py`](../../../src/prototypes/voice_delegation_hermes_agent/prompt_features.py) guarantees today) | all |
| **G1** Log replay of code paths | Replay every recorded tool call and output of the clean controls (all domains, plus mock) through the new relay | A1 / A1-lite trigger only on phone-field misses; every found-after-retry identity equals the expected one; all other outputs byte-identical; A3 attributions match a hand-labelled sample, with no false `spelled` or `heard as a word` | A1, A1-lite, A3 |
| **G2** Backend decision replay (needs P0.3) | One clean control run per domain with `backend_trace` on. Every write and transfer decision in **passing** tasks is labelled **U** (unchanged) or **P** (expected policy correction) **before** any arm is replayed (rules below). Each decision point is replayed with the arm's prompt, 3 samples at temperature 0 | **U:** same tool, same arguments, at the same point, in 3/3 samples. **P:** in 3/3 samples the arm first asks for confirmation (or agreement to the allowed change) with the correct details, and makes no tool call. Then, with the user's next turn replayed (the user's own later yes from the control, or a scripted "yes" if the control had none), it makes the same write with the same arguments. **Fix set:** report how many targeted decisions change; information only, wording is not tuned on it | A1-lite, A2, A3, B1–B3, C1, C2 |
| **G3** Mock and invented scenarios | `mock` domain, plus about 20 invented conversations per rule (consent edge cases, transfer-required policies, out-of-scope requests) | No new failure on mock; the invented cases behave as specified | all prompt fixes |
| **G4** Paired A/B | Control (`66f6c67`, same flags as geval) against arm: same tasks, interleaved in the same window, **5 trials each in every domain**, P0.1 gate clean in both. **First an A/A run** (two independent 5-trial control sets) | The scoring rules below: (a) the primary Pass¹ criterion, (b) the task-regression count, (c) diagnosis of every flip. All three must hold. P-labelled tasks from G2 must also pass in ≥ 3/5 arm trials (confirmation, then completion end to end) | **each fix alone, then all fixes combined** (also each phase's cumulative set) |

**G2 labelling rules (fixed before any arm is replayed).**
- **P (expected policy correction):** a write where the control made the call without the confirmation the policy
  requires: no summary with the details, followed by an explicit yes from the user to that summary, earlier in the
  call (B1). Also a reduced or different change made without the user agreeing to it (B2).
- **U (unchanged):** every other write, and every transfer.
  - A required transfer is always U. A required transfer that the arm delays by extra steps fails U (C1, C2).
- Labels come from the control's transcript, by a rule-based pass refined from E1, plus a hand check of every P
  label. They are recorded in the G2 report before any arm output is seen.

**Scoring rules (G4).**
- **Primary score: Pass¹ per domain**, i.e. tau2's average reward. For task *i* with *k* = 5 trials, *pᵢ* is the
  fraction of trials with reward 1. Pass¹ = mean over tasks of *pᵢ*.
- Pass^k for k > 1 is reported as secondary information only.
- **Δ** = Pass¹(arm) − Pass¹(control), on the same tasks.
- **Noise band *h*** (per domain, from the A/A run):
  - compute Δ_AA = Pass¹(control set 2) − Pass¹(control set 1);
  - draw 10,000 bootstrap resamples of the **tasks** (paired: a task keeps its *p* in both sets) and recompute Δ_AA
    on each;
  - *h* = the 97.5th percentile of |Δ_AA| over the resamples.
- **(a) Primary criterion:** Δ ≥ −*h* in every domain. Report Δ, *h* and the paired-bootstrap 95% interval of Δ.
- **(b) Task regressions:** a task regresses if *p*_control ≥ 3/5 and *p*_arm ≤ 2/5. The number of regressed tasks
  per domain must be ≤ the A/A count under the same definition (set 1 → set 2).
- **(c) Investigation:** every task with *p*_arm < *p*_control by ≥ 2/5, regressed or not, is diagnosed from its
  timeline (as in `per_task_diagnoses.md`). If the cause is the fix, the fix is rejected or rewritten using
  non-scored data only, whatever (a) and (b) say.

**Why the A/A step matters:** about 10% of tasks flip between identical single-trial runs. Without a measured noise
band, a "regression" can't be told apart from noise, and neither can an improvement.

**Clean baselines.** The geval telecom run is **not** a clean control: 22 of its tasks were hit by 429 stalls, and 6
failures are infra.
- Before G2 and G4, a fresh control is run per domain at `66f6c67` with `backend_trace` on, accepted only if the
  P0.1 gate is clean. The retail control is r3-like: no 429s.
- The no-regression set for G2 and the control for G4 come from these clean controls, not from the geval runs.
- The geval runs are used only to size exposures (E1–E4).

**What the gates can and cannot show.** Five trials per arm shrink the noise but cannot prove the absence of a
regression on a task the arm breaks only rarely. The gates give evidence within measurement limits.
- The decision replay (G2) checks every passing decision directly.
- The per-task investigation (G4c) makes sure every observed flip is explained.
- Any score claim states the trials, the A/A band and the investigated flips.

**Rollback:** every fix is its own flag. The deployed profile pins the flag set, and
[`cli/fingerprint_check.py`](../../../src/prototypes/voice_delegation_hermes_agent/cli/fingerprint_check.py) verifies it per session. The G2 harness would
follow the pattern of [`cli/delegation_replay.py`](../../../src/prototypes/voice_delegation_hermes_agent/cli/delegation_replay.py) (gate G3 of the prototype
plan).

*Implementation note:* the G1 tool is [`cli/relay_replay.py`](../../../src/prototypes/voice_delegation_hermes_agent/cli/relay_replay.py)
and the G2 tool is [`cli/backend_decision_replay.py`](../../../src/prototypes/voice_delegation_hermes_agent/cli/backend_decision_replay.py).
