## 1. What the three runs say

1. **Once the user is identified, about 70% of tasks pass in every domain:** 26 / 36 airline, 52 / 72 retail and
   27 / 40 telecom. Unidentified tasks rarely pass: 7 / 14, 5 / 42 and 6 / 74. Identification decides most of the gap
   between domains.
2. **Issue 1, telecom `id_format`: 64 of 81 failures.**
   - The number is heard right, but the backend sends `5551232002`. tau2's `get_customer_by_phone` needs an exact
     string match (`tau2-bench-smasurekar/src/tau2/domains/telecom/tools.py:61`), and every number in the DB has
     dashes.
   - Across the run there were 144 undashed calls (0 succeeded) and 41 dashed calls with the right digits (41
     succeeded).
   - The `spelling_v2` rule then forbids the one retry that would work: "do not retry with a guess or a variant". So
     the agent asks for a re-spelling, resends the same string (34 failed tasks have an identical repeat), and falls
     back to date of birth, which the simulated user doesn't know. The call ends `###OUT-OF-SCOPE###` or `###STOP###`.
   - Neither the telecom policy nor the tool description gives the format.
3. **Issue 2, `id_misheard`: 30 of 57 retail failures, 7 of 17 airline, 4 of 81 telecom.** The ASR loses or changes
   letters and digits. The agent's recovery then wastes the few repeats the simulated user allows: its guidelines
   allow repeating details "once or twice", and multiple requested pieces are given "one at a time"
   (`tau2-bench-smasurekar/data/tau2/user_simulator/simulation_guidelines_voice.md`). Mechanically, over the retail
   run:
   - 21 failed lookups sent a zip that was not 5 digits (`1912`, `191222`, `782640`, …);
   - 37 failed lookups differed from the right identity only by a doubled letter or digit (`ROSI`, `Isabela`, `Arav`);
   - 14 failed lookups resent an identical failed call;
   - the agent often re-asked one field and kept the other wrong one (5, 26, 91, 92). It also never asked for a
     spelling (44, 92), invented a digit (70), took "Dip" from "zip" as a surname (30), or put the email's letters
     into a name + zip lookup (35).
4. **Not every identity failure reaches a lookup.**
   - Retail 6 and 8 never made one: the user gave only a username.
   - Airline 39 had its only attempt rejected locally as an incomplete ID.

   A hook on a lookup result can't help these (§6).
5. **Other issues (deferred, §5–§6):**

   - transfers, 8;

## 2. How the backend prompt is built today, and where domain text can go

You asked first whether the Hermes backend can take domain-specific system-prompt text, and where policy lives.

**The final Hermes system prompt** is Hermes' own base prompt, then `SOUL.md`, then the voice platform hint, then
`backend_system`. `backend_system` is rendered by the gateway for each session from
`config/prompts.backend.yaml`:

```
backend_system (prompts.backend.yaml:18-60)
  ├─ base text (live voice call, context lines)                     all domains
  ├─ {% if features.spelling_v2 %} spelling rule {% else %} … {% endif %}   all domains
  ├─ <policy>{{ instructions }}</policy>                            ← tau2's voice instruction + domain policy.md
  ├─ {% if features.spoken_output %} <spoken_output> …              all domains
  └─ {% if features.write_consent %} <consent> …                    all domains
```

**The policy reaches the backend, not the frontend.**
1. tau2 sends `AUDIO_NATIVE_VOICE_INSTRUCTION` + `policy.md` as `session.update.session.instructions`
   (`tau2-bench-smasurekar/src/tau2/agent/discrete_time_audio_native_agent.py:99-141`).
2. The voice server forwards the instructions to the gateway only, because `instructions.apply_to: [backend]`
   (`delegation_agent.yaml:84-85`, `engine/turn_manager.py:295`).
3. The gateway renders them into `<policy>` (`backend/controller.py:697`).
4. The worker passes the result to Hermes as `ephemeral_system_prompt` (`worker/hermes_adapter.py:225`).

So policy-type rules belong in the backend system prompt, as you expected. The frontend never sees the policy.

**What is domain-specific today:**
- Only the tau2 policy text and the tool list. Both arrive at run time.
- No prompt file, profile or feature is selected by domain.
- `backend_catalog_sha256` hashes the single catalog file. `backend_system_sha256` differs per domain only because
  the policy is inside it.
- The voice-side tool-argument rules (`config/voice/tau3.yaml`) are keyed by tool name. They act on every domain that
  has the tool: the `get_user_details.user_id` rule fires on airline and retail.

**Domain-specific backend text is possible with a small, additive change.**
- **Recognise the domain from the tool list,** which is unambiguous in tau2:
  - telecom has `get_customer_by_phone`;
  - retail has `find_user_id_by_name_zip`;
  - airline has `get_reservation_details`;
  - mock has `create_task`.

  The tool names are in `tests/unit/prototypes/voice/fixtures/tau2_session_update/*.json`.
- **Render a per-domain block** in `backend_system`, behind a feature switch.

Nothing else changes: the protocol, the policy text and the other domains' prompts stay the same. Section 3.2 has
the design.

**Two other places carry domain-scoped behaviour without touching the system prompt:**
- **Tool-argument rules on the voice server.** They are keyed by tool name, so they are already domain-scoped.
  They work deterministically before the call reaches tau2.
- **Tool results.** The voice server relays every tool output (`tools/relay.py:117-136`), so it can append a short
  instruction to a specific failure of a specific tool. The model sees the text only when that failure happens.
  I3 and I4 use this.

## 3. Issue 1: telecom phone format (I1)

### 3.1 Options

| Option | What changes | Telecom passing tasks | Airline / retail | Deterministic | Verdict |
|---|---|---|---|---|---|
| **A. Telecom block in the backend prompt** (prompt) | The format, "a retry in this format is not a guess", then a grouped read-back | New text in the prompt; it agrees with every passing path | Byte-identical | No (LLM compliance) | **Recommended** |
| B. Hint in the "not found" result (prompt, failure-gated) | The same text, appended to `get_customer_by_phone` failures only | Unchanged unless a lookup failed | Unchanged | No | Good alternative; costs one failed call per task |
| C. Argument formatter (normalization) | `5551232002` → `555-123-2002` when there are exactly 10 digits | None visible | Unchanged (tool-scoped) | Yes | Fallback if A falls short (§3.3) |
| D. Edit `spelling_v2` for every domain | Allow format variants | — | Prompt changes in every domain | No | Rejected: it would touch airline and retail |

You suggested a brief prompt note listing the forms a number can take, so that the agent retries. Option A is that
note, kept in the telecom block so that it can't affect the other domains. It also resolves the `spelling_v2`
conflict locally: the block says a format retry is not a "variant", so the shared `spelling_v2` text stays the same.

### 3.2 Design (option A)

**Prompt block** (`prompts.backend.yaml`, new key and a new block after `</policy>`):

```yaml
# Per-domain notes, rendered into backend_system when features.domain_notes is on and the domain matches.
backend_domain_notes:
  telecom: |
    Phone numbers are stored with dashes, in the form 555-123-4567. Always pass a phone number
    to a tool in that form, even if the user did not say "dash". If a lookup by phone number
    fails and the failed argument contains exactly ten digits with only the formatting wrong,
    retry once with those same digits in XXX-XXX-XXXX form without asking the user anything;
    this is a format correction, not a guess. Never add, remove or change digits. Otherwise,
    or if that retry fails, read the digits you heard back in groups (for example "555, 123,
    4567") and ask the user to correct the number before asking for any other identifier.
```

```jinja
  {%- if features.domain_notes and domain_note %}

  <domain_notes>
  {{ domain_note }}
  </domain_notes>
  {%- endif %}
```

**Where domain-specific instructions go.** No existing section fits a telecom-only note:
- the opening paragraph and the `spelling_v2` paragraph are shared by every domain;
- `<policy>` is the τ² text, passed through word for word from `session.update.instructions`;
- `<spoken_output>` and `<consent>` apply to every domain and cover other topics.

`<domain_notes>` is therefore the one place for instructions that apply to a single domain. It sits right after
`</policy>`, so the model reads it as an addendum to that domain's policy. A later note, such as "retail zip codes
have five digits", is one more key under `backend_domain_notes`; no shared text changes. Every note must follow
these rules:
- **Facts, not policy.** A note states how data is formatted or how a tool behaves. It never adds to, relaxes or
  contradicts the τ² policy.
- **Short.** A few sentences at most, with a generic example rather than a value from the benchmark.
- **Behind its own switch.** Each note ships off by default and has its own feature name; `domain_notes` covers
  the telecom note only. Golden-prompt tests show that turning a note on changes only its own domain's prompt.

**Retry behaviour:**
- At most **one** format retry, and only when the failed argument has **exactly ten digits** and only its
  formatting is wrong (no dashes, other separators, spaces). The retry uses the same ten digits in the same order.
  It happens silently, before any question to the user.
- **No retry for any other digit count** (review 2, point 1). Dashes can't correct an incomplete or extra-digit
  number, and "putting it in the right form" would invite the model to drop a leading `1`, pad or truncate. Of the
  144 failed undashed `get_customer_by_phone` calls in the telecom run, 130 had exactly ten digits; the other 14
  (in 7 tasks: 0, 2, 8, 17, 18, 35 and 105) had 6 to 12: `555123`, `15551232002`, `+15551232002`, `25551232002`, `+335551232002`,
  `55512002`, `5551232`, … These go straight to the read-back, and the user corrects the number.
- A failed lookup that was already dashed also goes straight to the grouped read-back. Misheard digits are the case
  the 4 telecom `id_misheard` tasks (11, 18, 92, 99) show. A ten-digit misheard number (`5551230002`) gets one
  harmless dashed retry first.
- **No I1 target is lost by the stricter rule.** Every one of the 69 targets has at least one failed undashed call
  with exactly ten digits. Only #0 (`555123`) and #105 (`25551232002`) start with another count; under the new
  rule their first miss gets a read-back, and a later ten-digit miss gets the retry.
- Asking for another identifier comes only after the user has confirmed or corrected the digits.
- No other hint is added to telecom results: I3 and I4 exclude the telecom lookups (§4.1), so the two
  instructions never compete.
- **The example number is deliberately not the benchmark's.** Every telecom task uses `555-123-2002`; the example
  only shows the shape.

**Domain detection** (gateway):

```yaml
# gateway.yaml
domains:            # first match wins; a session with no match gets no domain note
  telecom: {tools_any: [get_customer_by_phone]}
  retail:  {tools_any: [find_user_id_by_name_zip, find_user_id_by_email]}
  airline: {tools_any: [get_reservation_details]}
prompt_features: {spelling_v2: true, spoken_output: true, write_consent: true, domain_notes: true}
```

- `backend/controller.py:691-705`: compute `domain` from the configured tool names once per configure, and render
  `backend_system(instructions=…, domain_note=…)`.
- **One render input for prompt and fingerprint.** `_fingerprint()` (`backend/controller.py:240-252`) renders
  `backend_system` with `instructions` only today. It must use the same `domain_note`, so that
  `backend_system_sha256` is the hash of what Hermes actually runs. A test asserts that the configured prompt and
  the fingerprinted prompt are byte-identical for every fixture.
- `prompt_features.py`: add `domain_notes: False` to `BACKEND_FEATURES`. `gateway.baseline.yaml` pins it off.
- **Fingerprint fields:**
  - add `backend_domain` to `_fingerprint()`;
  - forward it in the voice server's `_gw_session_configured` (`engine/turn_manager.py:793-805`), which today
    logs a fixed list of fields;
  - check it in `cli/fingerprint_check.py`.

**Tests** (`tests/unit/prototypes/delegation/test_fdh_golden_prompts.py`, `test_fdh_gateway_config.py`, and the
voice-server event test for `backend_configured`):
- With `domain_notes` **on**, `backend_system` for airline, retail and mock is byte-identical to the golden files.
  Add golden files for retail and telecom, rendered with the existing `tau2_session_update` fixtures.
- For telecom, the only difference is the `<domain_notes>` block.
- With the feature off, every render is byte-identical to today.
- Detection maps each fixture to its domain, and a tool list with no match gets no note.
- `backend_configured` carries `backend_domain`.

### 3.3 When to use the normalizer instead (option C)

- **The risk with A.** When the user said "dash", the dashed form still reached the tool only 27 times in 51, so the
  model drops dashes even when it hears them.
- **What protects A.** The silent retry in the block recovers on the second call.
- **When to add C.** Add the deterministic formatter if the I1 arm leaves more than about 10% of telecom tasks
  unidentified with the right digits. It is a new rule field, `digits_format: "###-###-####"`, applied only when the
  value has exactly 10 digits after stripping (`normalization/arguments.py:174-183`). It is safe for the other
  domains because rules are keyed by tool name.
- **Why it is not first.** You preferred a prompt fix, and a hidden rewrite would also hide whether the backend
  follows the policy.

### 3.4 Expected effect

- **Upper bound, from the telecom analysis.** If identification works as in the 40 identified tasks, the category
  pass rates give about 79 passes (0.69).
- **Practical expectation.** Allow for misheard digits and the remaining judgement failures: about **0.60–0.68** on
  telecom. This is a hypothesis for the arm to test.

## 4. Issue 2: identity misheard or mangled (I3, I4)

The ASR, not the agent, loses the letters, so no prompt can make the first lookup right. The fix is to make the
**recovery** efficient within the one or two repeats the simulated user allows:
1. **After the first miss, fix the doubtful field first** (I3).
2. **On a later miss, switch to a spelling the ASR handles better** (I4).

Both use one new relay hook, so they share the switch, the code path and the tests.

### 4.1 I3: a recovery hint in the first failed identity lookup's result

**Trigger and scope.**
- **Tools:** `find_user_id_by_name_zip`, `find_user_id_by_email` (retail) and `get_user_details` (airline's identity
  lookup).
- **Telecom is excluded** (`get_customer_by_phone`, `get_customer_by_id`): I1's own read-back covers it, and two
  instructions on the same result would compete (review 1, point 2). Telecom can be added later as its own arm,
  after I1.
- **What triggers a hint:** a tool output that matches the hook's own failure pattern (`result_hints.failure_pattern`,
  for example `^Error: .*\bnot found\b`). The hook doesn't depend on the retry guard or on a tool having an argument
  rule; today `tools/relay.py:130-131` detects failures only for guarded calls.
- **The hint is appended to that output** before `_send_result` (`tools/relay.py:117-136`), so the backend sees it
  as part of the tool result.

**Counter.**
- One per session, shared by the listed tools.
- It counts external misses (the failure pattern above) and local `invalid` answers for the same tools. The voice
  server already sends those for incomplete airline user IDs.
- It resets to zero when an identity lookup succeeds.
- **Miss 1 gets I3, miss 2 and later get I4.** No hint is added after the bound `max_hints: 3` is reached; the
  backend then sees the plain tool result, as today.
- A local answer never gets a hint appended. It only counts toward the next external miss.
- The relay logs `result_hint {call_id, tool, message_key, n}`.

```yaml
normalization:
  tool_arguments:
    result_hints:                      # independent of rules and retry_guard
      enabled: false
      tools: [find_user_id_by_name_zip, find_user_id_by_email, get_user_details]
      failure_pattern: '^Error: .*\bnot found\b'
      count_local_invalid: true
      max_hints: 3
      message_key: identity_not_found_hint            # miss 1 (I3)
      escalate_message_key: identity_not_found_hint_words   # miss 2 and later (I4); "" = repeat the first
```

**Hint text** (`voice_frontend_backend_agent/config/prompts.voice.yaml`). It is incremental because the simulated
user gives requested pieces one at a time, and long read-backs get cut off:

```yaml
identity_not_found_hint:
  content: |
    [Not found. At least one value you sent is wrong, possibly one the user spelled: speech
    recognition can drop or change letters even in a spelling. Keep the other fields for the
    next lookup, but none is confirmed until a lookup succeeds. Ask about one field at a time,
    starting with the most doubtful: a zip code that is not five digits, a name you only heard
    as a word, or a field whose versions differ. Read back only that field, letter by letter or
    digit by digit, and ask the user to confirm or spell it, saying "double S" for repeated
    letters. Build the next lookup from the latest value of each field, taken from what the user
    spelled rather than a word you heard; if that spelling differs from an earlier version
    (Ana after Anna), ask which is right first. Never fill in a missing letter or digit.
    After two misses with one method, offer the other method your policy allows.]
```

**Why each sentence is there**, from the per-task diagnoses:

| Sentence | Failed tasks it addresses |
|---|---|
| Keep the other fields provisionally; one field at a time, most doubtful first | 0 (re-spelled only the name, kept the wrong zip), 4 (6-digit zip never re-asked), 5, 44 (never asked to spell the first name), 92, 108 |
| A spelled field can still be wrong; differing versions are asked about | 26 (the spelled `I, S, A, B, E, L, L, A` was heard as `ISABELA`; the heard word "Isabella" was right) |
| From spelled letters, not heard words | 88 (spelled DAIKI never used), 90, 98 (spelled L-I, sent "Lee"), 30 ("Dip" from "zip"), 35 |
| Latest value per field | 91 (78705 heard, old 78005 sent) |
| Never fill in | 70 (invented the zip's last digit), 63 (expanded "H E N R" to HENRY) |
| Switch method after two misses | 14, 90 (email failed; never asked to spell the email), 35 |

**Fields are kept provisionally, never frozen** (review 2, point 2). Revision 2 said "keep any field the user has
already spelled or confirmed". A spelling is not proof that the ASR captured it: in retail 26 the user spelled
`I, S, A, B, E, L, L, A`, the ASR produced `ISABELA`, and the second lookup failed. The earlier word "Isabella" was
right, and only its last name was wrong. Revision 2's text would have told the backend to keep the wrong first name.
The hint now:
- keeps the other fields for the next lookup, but treats none as confirmed until a lookup succeeds;
- ranks malformed fields (a zip that is not five digits) and differing versions first;
- still builds the next lookup from the user's spelling, but asks first when that spelling differs from an earlier
  version of the field (26), instead of trusting either. The example in the hint ("Ana after Anna") is deliberately
  not the benchmark's name;
- lets the backend go back to a field the user already spelled once the more doubtful fields have been checked
  and found right.

Only a successful lookup confirms a field. A user saying "yes" to a read-back confirms what was read, so it ranks
that field last, but it doesn't rule it out. This matches what the ASR does to spelled input (§4.2).

**Dropped from revision 1:** the username → name sentence. Its targets (retail 6 and 8) never reached a lookup, so
a lookup hook can't serve them (§6).

**Exposure on passing tasks** (sentinels). These passing tasks had at least one external identity miss, so they
would see the hint:
- airline: 0, 2, 5, 8, 9, 18, 26, 31, 36, 43 and 47 (11);
- retail: 1, 2, 7, 17, 19, 25, 36, 37, 45, 48, 50, 51, 52, 53, 54, 55, 58, 60, 64, 65, 68, 80, 85, 93, 96, 97 and
  102 (27).

The 38 tasks split into two groups:

| Group | Count | Tasks | What the hint could change |
|---|---|---|---|
| Recovered to an identified user | 32 | The rest | A re-spelling (Sofia/Li, Mei, Chen, Ito), an email ↔ name + zip switch (36, 37, 54) or a zip fix (64). The hint asks for these moves |
| Passed without ever being identified | 6 | airline 0, 26; retail 25, 60, 65, 80 | Their tasks didn't need an identified user to pass. A hint that prolongs the identity loop could cost them, so they are the **highest-risk sentinels** |

**Tests:**
- the hint is appended only to the listed tools' outputs that match `failure_pattern`, never to a success, a
  transient error, an unlisted tool or a local answer;
- counter: a local invalid answer followed by an external miss gets the I4 key; a success resets the counter;
  nothing is appended after `max_hints`;
- with the switch off, outputs are byte-identical;
- the hook works with `rules: []` and `retry_guard.enabled: false`;
- the golden `local_tool_messages.txt` gains the new keys, and the old ones are unchanged;
- configuration loading: `result_hints` is parsed and validated, unknown or missing message keys fail at startup
  (§8).

### 4.2 I4: word-assisted spelling on a later miss (prompt only, experimental)

**Problem.** Isolated letters are the ASR's weakest input:
- doubled letters collapse ("R, O, S, S, I" → "R O S I", even after "two S's");
- the leading "A, A" is dropped;
- B, D, G and V swap.

Airline 14, 16, 17, 25, 37 and retail 9, 27, 38, 42, 63, 74, 75, 76 and 78 had 3–7 spellings that all came back
wrong. Words survive the ASR much better than letter names.

```yaml
identity_not_found_hint_words:
  content: |
    [Not found again. Keep the other fields for now; a field spelled before can still be the
    wrong one. Ask the user to spell only the field most likely wrong once more, using a word
    for each letter, for example "S as in Sam, A as in apple", and to say "double" for
    repeated letters. Use the first letter of each word; if a word and the spoken letter
    disagree, ask which is right. Read that field back once before you look it up. After two
    misses with one method, offer the other method your policy allows.]
```

- **Prompt only.** The backend reads "S as in Sam" as it is, so no transcript normalization is needed. The
  normalizer from revision 1 would have processed every transcript of the session, not only failure paths. It is
  deferred with the constraints the review asked for (§5.6).
- **Conflicts are confirmed, not resolved silently.** If the word and the spoken letter disagree, the backend asks
  the user which is right.
- **The method-switch rule is repeated,** because the I4 text replaces I3 on later misses.
- **Evidence still needed.** The simulated user follows the agent's spelling requests (tau2
  `simulation_guidelines_voice.md`: "offer to spell it out letter by letter"). It is unverified whether it uses
  words. The arm measures that, but its gate is task outcome (§7.3).

**Exposure on passing tasks.** These passing tasks had at least two misses with at least one external miss, so they
would see I4 at most (an upper bound, because the order of local and external misses isn't recorded in `tasks.json`):

## 5. Deferred fixes (designed, not in this plan)

These have a design and evidence, but they are not part of this plan. Each can be picked up later as its own arm,
under the rules of §7.

### 5.1 I2: field-shape checks and the retry guard (deferred)

- **What it would do.** Voice-server tool-argument rules in a new `config/voice/tau3_identity.yaml`:
  - a `find_user_id_by_name_zip.zip` that isn't 5 digits is never sent; it is answered locally with the existing
    read-back message;
  - `find_user_id_by_email` and `get_customer_by_phone` get a rule with no transform, which only enrolls them in the
    existing retry guard (`scope: rules`). An identical resend of a failed lookup is then answered locally
    (`tool_call_already_failed`) instead of becoming another tau2 error.
- **Evidence:**
  - 0 of 50 successful name + zip lookups had a non-5-digit zip;
  - 0 of 55 identical repeats succeeded (retail 14, telecom 41);

- **Why deferred.** With I1's silent retry and I3's digit-by-digit read-back on, most of its targets are covered.
  Pick it up if the I1 or I3 arm still shows identical resends or invalid zips.

### 5.2 C1: frontend dead-air guards (deferred)

**What it would do.** Two `apply_guards` checks in `frontend/decider.py`, each behind its own switch:
- **`ping_needs_answer`.** A check-in ("Hello? Are you still there?") with the backend IDLE never gets an empty
  DIRECT reply; it is delegated.
- **`promise_needs_delegate`.** A DIRECT "Let me …" while the backend is IDLE is delegated, so the promised action
  runs.

**Targets:** retail 22, 59, 81, 106 and 112. For example, 112 said "Let me repeat the second order number." six
times and never repeated it.

**Counts** (all three runs):

| Guard | Failed | Passed |
|---|---|---|

| Promise DIRECT in IDLE | 14 tasks | 8 tasks |

### 5.3 C2: same-item exchange guard (deferred)

- **What it would do.** A local answer for `exchange_delivered_order_items` or `modify_pending_order_items` when
  **every** new item equals its old item; policy allows only a different option.
- **Evidence.** It fired once in the three runs, on retail 107 (failed). Retail 36 (passed) had only one unchanged
  pair and would pass through.

### 5.4 C3: key figure first, interim answer in long chains (deferred)

- **What it would do.** A `spoken_output_v2` variant:
  - the asked-for number or fact goes in the first sentence;
  - before a chain of more than three lookups, say in one sentence what you already have.
- **Targets:** airline 11 and 21; retail 18, 28, 31, 46, 99, 100 and 111.
- **Why deferred.** It changes the system prompt of every session, so it is not trade-off free by construction.

### 5.5 C4: numbers as digits in written answers (deferred)

- **What it would do.** Add "Write amounts and counts as digits" to `spoken_output`.
- **Target:** airline 3, where tau2's communicate check wanted "4" and got "four".
- **Why deferred.** It changes every session's prompt and fixes a benchmark artifact.

### 5.6 Phonetic-spelling transcript normalizer (deferred, I4's voice side)

**What it would do.** Turn "X as in Word" into the letter, and "double X" into "XX", in the text the agents see.

**Why deferred.** A transcript normalizer runs on every turn of the session. It could change first-try successes,
ordinary speech, and identifiers given after authentication. Keeping the raw ASR text doesn't protect the agents,
because they act on the normalized text.

**Constraints if it is picked up:**
- **Rewrite only explicit spelling patterns,** a single letter followed by "as in" and a word, and only while a
  spelling request is open. "Open" means armed by an I4 hint in that session and disarmed by the next lookup.
- **Never resolve a conflict silently.** When the word's initial and the spoken letter differ, keep both visible
  ("B (as in David)") so the backend asks.
- **Replay before an arm:**
  - ordinary speech and the successful spelling paths of the three runs must come out byte-identical;
  - the spelling-hold fixture must keep its held/continued counts.

## 7. Non-regression: how the fixes avoid costing passing tasks

### 7.1 By construction

1. **Every fix is behind its own switch.** Code defaults are off. The current fixes-on configuration
   (`tau3_eval.yaml` + `gateway.yaml`, `config_hash 06baf96e3baf`) is the **control**, and it must render
   byte-identically with every new switch off (golden tests).
2. **I1 is domain-scoped.** Airline, retail and mock prompts are byte-identical with `domain_notes` on.
3. **I3 and I4 are failure-gated and prompt-only.** They appear only in a failed airline or retail identity
   lookup's result. Telecom results and sessions whose first lookup succeeds are unchanged. No transcript
   normalization is added.

This limits **which sessions can change**. It doesn't prove that a session which does change still passes. That is
what §7.3 measures.

### 7.2 Mechanical checks on the archived runs (done for this plan)

| Check | Result |
|---|---|
| Successful `get_customer_by_phone` without dashes | 0 of 144 undashed calls; 41 of 41 dashed calls with the right digits succeeded |
| Failed undashed phone calls by digit count (I1's retry condition) | 130 with exactly ten digits; 14 with 6–12 digits, in 7 tasks. All 69 I1 targets have a ten-digit miss (§3.2) |
| Sessions whose first identity lookup succeeded (unchanged under I3 and I4) | 23 / 44 airline, 45 / 107 retail |
| Passing tasks that would see the I3 hint | 11 airline, 27 retail; 6 of them were never identified (§4.1) |
| Passing tasks that could see the I4 hint | at most 7 airline, 16 retail (§4.2) |
| Primary I3 and I4 targets whose recorded path fires the trigger | All 39 (§9) |

Before each arm runs, replay the archived tool outputs and local answers through the relay and assert two things:
- a hint is appended only on the failures counted above, with the expected key;
- every other output is byte-identical.

### 7.3 Evaluation gate

**Per-task paired results, not totals.** Every arm is compared with a fresh control on the same host and commit,
task by task. Matched pass totals can hide losses that are offset by gains. A **repeatable loss** is a task that
passes in at least 2 of 3 control trials and fails in at least 2 of 3 arm trials.

**What every arm reports:**
- pass^1 per task and per domain;
- identification rate and time to identification;
- number of failed lookups;
- abandonment: user stops after "taking too long", ping rate, `too_many_errors`;
- per-turn latency;
- policy correctness: DB and action checks, and transfers.

| Stage | Arm | Runs | Gate |
|---|---|---|---|
| 0 | Offline | Unit, configuration-loading and golden tests; the §7.2 replays; `fingerprint_check` | All pass |
| 1 | **I1**, telecom | Full telecom, 3 trials per arm | Identification rate up; no repeatable loss; no rise in abandonment or wrong transfers |
| 2 | **I3**, airline and retail | Full airline and retail, plus the I3 sentinels (§4.1) with 3 trials | No repeatable loss, with every changed sentinel inspected, the 6 never-identified ones first; pass^1 up on the targets |
| 3 | **I4** on top of I3 | Airline and retail, plus the I4 sentinels (§4.2) with 3 trials | **Task outcomes:** no repeatable loss against stage 2 and pass^1 up on the I4 targets. The share of users spelling with words is reported, not gated |
| 4 | **Final combination** I1 + I3 (+ I4 if it passed) | All three domains, 3 trials | No repeatable loss against the control in any domain. This is the configuration that would ship |

**Rules for every stage:**
- one change per arm until stage 4;
- a fresh paired control, never a comparison with these 2026-09-30 runs;
- the expected fingerprint checked per session (`cli/fingerprint_check.py`, with `backend_domain` and the new
  switches).

**Limits of the evidence.** Three trials per arm detect repeatable losses only. A rare loss, failing in one trial in
three, can still pass the gate. Investigate every task that changed outcome in either direction before calling a fix
trade-off free.
